### <a name="_qmphm5d6rvi3"></a>**Решение**

Ниже представлены ключевые архитектурные решения, оформленные в формате Y‑Statement.

---

**Решение 1. Применение паттерна Strangler Fig для постепенной миграции**

| Элемент | Описание |
|---------|----------|
| **Контекст** | Монолитное приложение с тесной связанностью, высокими рисками при изменении, невозможностью масштабировать отдельные компоненты. |
| **Причина** | Необходимо перейти к микросервисной архитектуре без остановки бизнеса, минимизируя риски и затраты. |
| **Принято** | Использовать паттерн Strangler Fig: постепенно выносить функциональность в новые микросервисы, маршрутизируя часть трафика на них, пока монолит не будет полностью замещён. |
| **Отклонено** | Полная переписывание системы с нуля (высокий риск, длительный простой) или оставление монолита без изменений (не решает проблемы). |
| **Цель** | Обеспечить плавный переход, сохраняя работоспособность системы на каждом этапе, снизить риски и стоимость миграции. |
| **Компромиссы** | Дополнительные усилия на поддержку параллельной работы двух систем, сложность маршрутизации и синхронизации данных. |

---

**Решение 2. Первый выделяемый модуль – BookingService**

| Элемент | Описание |
|---------|----------|
| **Контекст** | Бронирование – одна из самых нагруженных и критичных функций. В текущем монолите `BookingService` активно использует другие сервисы (пользователи, отели, отзывы, промокоды), но все вызовы легко заменяются на REST. |
| **Причина** | Высокая нагрузка на бронирования, бизнес-критичность, наличие чётких границ (все зависимости идут через публичные методы), отсутствие JPA-связей с другими сущностями – это снижает сложность выноса. |
| **Принято** | Начать миграцию с `BookingService` – создать отдельный микросервис, перенести код и переключить трафик. |
| **Отклонено** | Вынос `HotelService` первым (меньше точек интеграции, но бронирование даёт больше бизнес-эффекта) или вынос всех сервисов сразу (недостаток ресурсов). |
| **Цель** | Быстро получить измеримый результат, разгрузить монолит в самом нагруженном направлении, обеспечить масштабируемость для пиковых нагрузок. |
| **Компромиссы** | Необходимо реализовать REST-клиенты для вызова монолита, возможное увеличение задержек на первом этапе. |

---

**Решение 3. Последовательность выноса сервисов**

| Элемент | Описание |
|---------|----------|
| **Контекст** | После выноса BookingService остаются другие поддомены: отели, отзывы, промокоды, пользователи. Анализ зависимостей показывает, что `HotelService` и `ReviewService` не зависят от других, а `PromoCodeService` зависит от `AppUserService`. |
| **Причина** | Минимизировать сложность интеграции на каждом шаге – выносить сначала независимые сервисы, затем зависимые. |
| **Принято** | 1. BookingService (уже вынесен); 2. HotelService (независим); 3. ReviewService (независим); 4. PromoCodeService (зависит от AppUserService, но после выноса ReviewService монолит облегчается); 5. AppUserService (последний, после него монолит может быть выключен). |
| **Отклонено** | Другие порядки (например, сначала AppUserService) – привели бы к дополнительным циклическим зависимостям на этапе миграции. |
| **Цель** | Последовательно уменьшать монолит, сохраняя работоспособность и минимизируя количество изменений на каждом этапе. |
| **Компромиссы** | Длительный общий срок миграции; на промежуточных этапах часть вызовов идёт к монолиту, часть – к новым сервисам, увеличивая сложность маршрутизации. |

---

**Решение 4. Использование синхронного REST для межсервисного взаимодействия (на первом этапе)**

| Элемент | Описание |
|---------|----------|
| **Контекст** | После выноса BookingService, ему необходимо обращаться к оставшимся в монолите сервисам для проверок и получения данных. |
| **Причина** | REST – простой, понятный, хорошо поддерживается Spring, позволяет быстро реализовать интеграцию без дополнительной инфраструктуры. |
| **Принято** | Использовать REST-вызовы (Feign-клиенты) для синхронного получения данных от монолита. В будущем, при росте нагрузки, рассмотреть переход на асинхронное взаимодействие (Kafka). |
| **Отклонено** | Использование асинхронной шины (Kafka) на начальном этапе (усложняет реализацию и отладку) или прямые JDBC-запросы к БД монолита (нарушает принцип владения данными). |
| **Цель** | Минимизировать сложность и время реализации первого выноса, обеспечить прозрачность вызовов. |
| **Компромиссы** | Увеличение задержек, синхронная связанность (временная зависимость), сложность обработки частичных сбоев. |

---

**Решение 5. Применение паттерна Saga для обеспечения согласованности данных**

| Элемент | Описание |
|---------|----------|
| **Контекст** | При создании бронирования данные изменяются в разных сервисах (бронирование, статус отеля, статистика и т.д.). Необходима согласованность при сбоях. |
| **Причина** | В монолите транзакции были локальными; в микросервисах требуется распределённая координация. Отсутствие JPA-связей упрощает разделение, но усложняет целостность. |
| **Принято** | Внедрить паттерн Saga (координация через оркестратор) для компенсации операций при ошибках (например, отмена бронирования, если не удалось применить промокод). На начальном этапе использовать простую логику компенсации внутри BookingService, в дальнейшем – выделенный оркестратор. |
| **Отклонено** | Двухфазный коммит (2PC) – слишком тяжёлый, блокирующий, не подходит для распределённых систем; игнорирование согласованности (риск потери данных). |
| **Цель** | Обеспечить атомарность бизнес-операций, сохраняя данные консистентными даже при сбоях отдельных сервисов. |
| **Компромиссы** | Дополнительная сложность реализации, увеличение времени выполнения операций, необходимость хранения состояния саги. |

---

**Решение 6. Использование API Gateway (Kong)**

| Элемент | Описание |
|---------|----------|
| **Контекст** | Клиенты (фронтенд, партнёры) взаимодействуют с разными сервисами. Необходима единая точка входа, маршрутизация, аутентификация, ограничение трафика. |
| **Причина** | Упростить взаимодействие с клиентами, централизовать безопасность, обеспечить гибкую маршрутизацию при постепенном переключении трафика. |
| **Принято** | Развернуть API Gateway на базе Kong (или Spring Cloud Gateway) для приёма всех внешних запросов и их перенаправления в соответствующие сервисы (монолит или микросервисы). |
| **Отклонено** | Прямое обращение клиентов к каждому сервису (увеличивает сложность, нарушает инкапсуляцию) или использование балансировщика без gateway (нет гибкости маршрутизации). |
| **Цель** | Обеспечить единый вход, упростить управление версиями API, реализовать канареечные релизы и постепенное переключение трафика. |
| **Компромиссы** | Дополнительный компонент в инфраструктуре, потенциальная точка отказа (требуется репликация), небольшая задержка на маршрутизацию. |

---

**Решение 7. Отказ от рефакторинга монолита**

| Элемент | Описание |
|---------|----------|
| **Контекст** | Монолит работает стабильно, его кодовая база проверена годами. Любые изменения в нём несут риск появления новых ошибок. |
| **Причина** | Снизить риски и затраты на миграцию – не переписывать существующий код, а только выносить готовые модули. |
| **Принято** | Не рефакторить монолит, сохранить его как есть. В процессе выноса сервисов соответствующие части кода просто удаляются (или деактивируются), но без изменений в оставшейся логике. |
| **Отклонено** | Проведение рефакторинга для улучшения структуры перед выносом (увеличивает время, риск, требует глубокого понимания всего кода). |
| **Цель** | Минимизировать стоимость миграции, сохранить стабильность работающей системы на время перехода. |
| **Компромиссы** | В монолите остаются «хвосты» (неиспользуемые зависимости, старые методы), которые могут мешать, но они неактивны; со временем монолит полностью выключается. |

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

| Альтернатива | Описание | Причина отклонения |
|--------------|----------|---------------------|
| Полная переписывание системы | Создание всех микросервисов с нуля и одномоментный переход | Высокий риск, длительный простой, большие затраты |
| Вынос HotelService первым | Начать с поиска отелей, т.к. он тоже высоконагружен | Меньше бизнес-эффекта, чем у бронирования; бронирование даёт больше точек интеграции для проверки подхода |
| Оставить монолит | Не проводить миграцию | Не решает существующие проблемы (масштабирование, сложность разработки) |
| Вынос всех сервисов сразу | Создать несколько микросервисов параллельно | Недостаток ресурсов (команда 2 Java-разработчика), сложность координации |

### **Риски и ограничения**

1. **Увеличение сетевой задержки** – REST-вызовы вместо внутрипроцессных. Снижение: кэширование, асинхронность в перспективе.
2. **Сложность распределённых транзакций** – требуется внедрение Saga. Компенсируется чётким проектированием саг и использованием оркестратора.
3. **Временная сложность миграции** – поддержка двух систем. Управляется за счёт поэтапного переключения и мониторинга.
4. **Риск ошибок при интеграции** – изменение форматов данных. Снижается контрактным тестированием и постепенным включением.
5. **Дополнительные затраты на инфраструктуру** – Kong, Zipkin, кластеры БД. Компенсируются улучшенной управляемостью.
6. **Необходимость обучения команды** – новые технологии и подходы. Планируются внутренние тренинги и спринты для изучения.

### **План миграции (Strangler Fig)**

1. **Этап 1. Вынос BookingService**
    - Перенести `BookingController`, `BookingService`, `BookingRepository` и сущность `Booking` в новый сервис.
    - Заменить локальные вызовы на REST-клиенты к монолиту.
    - Настроить API Gateway для маршрутизации части запросов на новый сервис.

2. **Этап 2. Переключение трафика на BookingService**
    - Постепенно увеличивать долю запросов, направляемых в микросервис (канареечный релиз).
    - Мониторить ошибки и производительность.
    - При успехе переключить 100% трафика и удалить `Booking*` код из монолита.

3. **Этап 3. Вынос HotelService**
    - Выделить `HotelService` (независимый) в отдельный микросервис.
    - Настроить Kong для  `BookingService`, чтобы он вызывал новый `hotel-service` вместо монолита.

4. **Этап 4. Вынос ReviewService**
    - Выделить `ReviewService` (независимый) в отдельный микросервис.
    - Настроить Kong для  `BookingService`, чтобы он вызывал новый `review-service`.

5. **Этап 5. Вынос PromoCodeService**
    - Выделить `PromoCodeService` в отдельный микросервис.
    - Настроить Kong для `BookingService` на вызов нового `promocode-service`.

6. **Этап 6. Вынос AppUserService**
    - Последним вынести `AppUserService`.
    - Настроить Kong для  `BookingService` и `PromoCodeService`, чтобы он вызывал новый `review-service`.
    - После этого монолит становится пустым и может быть отключён.

7. **Этап 7. Оптимизация и завершение**
    - Внедрить распределённую трассировку (Zipkin), централизованное логирование.
    - Настроить масштабирование и мониторинг.
    - Провести ретроспективу и оптимизировать взаимодействия (возможно, перейти на асинхронное взаимодействие через Kafka).

Финальную диаграмму контейнеров дикомпозиции монолита на микросервисы можно увидеть в файле `С4_С2_Final.puml`.
