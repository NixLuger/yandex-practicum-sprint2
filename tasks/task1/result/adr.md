### **Нефункциональные требования**

| № | Требование |
|---|------------|
| 1 | **Масштабируемость** – возможность горизонтального масштабирования компонента бронирований независимо от остальных функций, для обработки пиковых нагрузок (до 10 000 бронирований в час). |
| 2 | **Независимость разработки** – разные команды (например, команда бронирований и команда отелей) должны иметь возможность разрабатывать, тестировать и развёртывать свои сервисы независимо друг от друга. |
| 3 | **Отказоустойчивость** – при сбое одного из сервисов остальные должны продолжать работу (например, если сервис промокодов недоступен, бронирование всё равно должно создаваться, но без скидки). |
| 4 | **Производительность** – время отклика на создание бронирования не должно превышать 500 мс (95-й процентиль) в штатном режиме, с учётом сетевых задержек при межсервисных вызовах. |
| 5 | **Надёжность данных** – обеспечение согласованности между разными сервисами (распределённые транзакции или паттерны компенсации), поскольку сущности теперь живут в разных базах данных. |
| 6 | **Мониторинг и трассировка** – централизованный сбор логов, метрик и распределённой трассировки для быстрого выявления проблем в цепочке вызовов. |
| 7 | **Безопасность** – защита API с помощью аутентификации/авторизации (JWT) и ограничение доступа к чувствительным операциям (например, создание бронирования только для аутентифицированных пользователей). |
| 8 | **Непрерывная поставка** – возможность развёртывания каждого микросервиса независимо через CI/CD пайплайн (Docker, Kubernetes). |

### **Решение**

#### Целевое состояние системы

Мы переходим к постепенному выносу функциональности из монолита с использованием паттерна **Strangler Fig**. Первым выделяется **Booking Service** – сервис бронирований. После выноса система будет состоять из двух контейнеров (на уровне C2):

1. **Hotelio Monolith (остаток)** – содержит функциональность по управлению отелями, пользователями, промокодами и отзывами.
2. **Booking Microservice** – отвечает за создание, хранение и чтение бронирований.

Взаимодействие между ними осуществляется синхронно через REST API (позднее может быть заменено на асинхронное, но на первом этапе оставляем REST для простоты).

Диаграмма контейнеров (C2) целевой системы приведена в файле C4_C2.puml

На уровне компонентов (C4) внутренняя структура **Booking Microservice** включает:

- `BookingController` – REST-эндпоинты (`listBookings`, `createBooking`)
- `BookingService` – бизнес-логика, включая приватные методы `validateUser`, `validateHotel`, `resolveBasePrice`, `resolvePromoDiscount`
- `BookingRepository` – доступ к таблице `Booking` в своей БД.


Если исключить из монолита имеет аналогичную структуру, но без `Booking*` компонентов (см. приложенную диаграмму `С4_С4_without.puml`), то видно, что между сервисами нет перекрёстных вызовов, и контроллера по поддоменам строго используют только свои сервисы и репозитории, что позволяет экстрактировать поддомены в микросервисы без нарушений логики работы всей системы.
Единственный сервис, который использует сторонний репозиторий это `PromoCodeService`, который использует `AppUserService`, что определяет строгую последовательность действий в плане перехода на микросервисы.

**Обоснование выбора первого модуля (BookingService):**

- **Высокая нагрузка** – на бронирования приходится основной пиковый трафик, что делает его критичным для масштабирования.
- **Независимость** – из анализа кода видно, что `BookingService` обращается к другим сервисам только через публичные методы, которые легко могут быть заменены на REST-вызовы.
- **Бизнес-ценность** – бронирование – ключевая операция, её выделение даёт наибольший эффект для бизнеса.
- **Отсутствие жёстких связей в моделях данных** – сущности (Booking, Hotel, User, PromoCode, Review) не имеют JPA-связей (аннотаций `@OneToMany` и т.д.), что позволяет легко разделить БД, опираясь только на идентификаторы. Это сильно упрощает вынос.

Вторым шагом планируется выделить **HotelService** (поиск отелей) – также высоконагруженный и не имеющий зависимостей от других сервисов (по диаграмме `С4_С4_without.puml` видно, что он независим).

Тритьим шагом планируется вынести **ReviewService**, т.к. он ни от кого не зависит и вынос данного сервиса в микросервис является самым простым

Четвертым шагом планируется вынести **PromoCodeService**, т.к. он зависит от AppUserService и в итоге AppUserService остаётся единственным работающим сервисом в монолите.

Пятым шагом планируется вынести **AppUserService**, т.к. он последний микросервис. 

Монолит при этом можно не рефакторить вовсе. Т.к. любой рефакторинг увеличивает риски, что работающее годами проверенное ПО может начать глючить. 
Уменьшить риски и сократить ресурсные затраты если не трогать монолит.

Итого последовательность выноса:
1. BookingService
2. HotelService
3. ReviewService
4. PromoCodeService
5. AppUserService


#### Технологический стек

- **Java 17 / Spring Boot 3** – для всех микросервисов (сохраняем единый стек).
- **PostgreSQL** – как основная СУБД (каждый сервис использует свою схему/БД).
- **Docker** – контейнеризация и оркестрация через Kubernetes (в будущем).
- **Kong** – API Gateway для балансировки и управления трафиком.
- **Zipkin** – для мониторинга и трассировки.

#### Ключевые архитектурные решения

- Используем **синхронные REST-вызовы** между сервисами на начальном этапе – это просто реализовать и дебажить. При росте нагрузки перейдём на асинхронное взаимодействие через события (Kafka) для улучшения отказоустойчивости и уменьшения задержек.
- Для обеспечения согласованности данных при распределённых операциях будем применять паттерн **Saga** (координация через оркестратор или хореографию) – в частности, для отката бронирования при сбое проверок. Однако на первом этапе сохраняем простые транзакционные границы внутри каждого сервиса и компенсирующие действия на уровне бизнес-логики.
- Разделяем базы данных: каждый сервис владеет своей схемой (не допускаем прямых SQL-запросов к чужим таблицам).
- Внедряем API Gateway (например, Spring Cloud Gateway) для маршрутизации и аутентификации, чтобы клиенты (фронтенд, партнёры) обращались к единому входу.

### **Альтернативы**

| Альтернатива | Описание | Причина отклонения |
|--------------|----------|---------------------|
| **Полная переписывание системы** | Создание всех микросервисов с нуля и одномоментный переход. | Огромный риск, длительный простой бизнеса, высокая стоимость, невозможность поэтапного внедрения. |
| **Вынос другого сервиса первым (например, HotelService)** | Начать с выноса поиска отелей, т.к. он тоже высоконагружен. | HotelService не требует валидации других сущностей, но у него нет таких зависимостей, как у Booking, которые показывают больше точек интеграции. Бронирование более критично для бизнеса и даёт больше преимуществ при масштабировании. |
| **Оставить всё как есть (не мигрировать)** | Продолжать развивать монолит. | Не решает существующие проблемы: невозможность независимого масштабирования, сложность разработки, высокий риск регрессий. |
| **Вынос всех сервисов сразу** | Создать сразу несколько микросервисов и постепенно переключать трафик. | Недостаток ресурсов (команда 2 Java-разработчика) – слишком высокая сложность координации, увеличивает время до первого релиза. |

### **Недостатки, ограничения, риски**

1. **Увеличение сетевой задержки** – вместо внутрипроцессных вызовов теперь используются REST-запросы, что может повысить время отклика. Для снижения риска вводим кэширование (например, для проверок статуса отеля и пользователя) и асинхронные механизмы.
2. **Сложность распределённых транзакций** – отсутствие жёстких связей между сущностями (как показано в моделях) упрощает разделение, но в то же время это является недостатком монолита, так как согласованность данных не обеспечивалась на уровне БД. При переходе на микросервисы требуется внедрение паттернов Saga, что увеличивает сложность разработки и тестирования.
3. **Временная сложность миграции** – поэтапный вынос требует поддержания двух систем (монолит и новый сервис) параллельно, что создаёт дополнительные накладные расходы на синхронизацию данных и маршрутизацию запросов.
4. **Риск ошибок при интеграции** – из-за изменения форматов запросов/ответов при переходе от локальных вызовов к REST могут возникать несоответствия. Покрытие интеграционными тестами и контрактное тестирование (Pact) снизят этот риск.
5. **Дополнительные затраты на инфраструктуру** – запуск нескольких сервисов требует больше ресурсов для оркестрации, мониторинга и логирования. Однако это компенсируется улучшенной управляемостью.
6. **Необходимость обучения команды** – разработчики должны освоить новые подходы (распределённые системы, работа с сетью, Kubernetes). Проведём внутренние тренинги и выделим время на исследование.

### **План миграции (Strangler Fig)**

1. **Этап 1 (вынос логики бронирования)**
    - Перенести код `BookingController`, `BookingService`, `BookingRepository` и сущность `Booking` в новый сервис.
    - Заменить локальные вызовы `AppUserService`, `HotelService`, `ReviewService`, `PromoCodeService` на REST-вызовы к монолитуя.
    - Настроить маршрутизацию: часть запросов (например, `POST /api/bookings`) направлять в новый сервис, остальные пока оставить в монолите.

2. **Этап 2 (переключение трафика)**
    - Постепенно увеличивать процент запросов, идущих в микросервис, с использованием канареечных релизов (например, с помощью заголовков или балансировщика).
    - Мониторить ошибки и производительность.
    - При успехе полностью переключить трафик на микросервис и удалить `Booking*` код из монолита.

3. **Этап 3 (вынос HotelService)**
    - Аналогично выделить `HotelService` в отдельный микросервис, теперь он будет независим (не имеет зависимостей от других сервисов, кроме своей БД).
    - После выноса настроить маршрутизацию на `booking-service`, чтобы он вызывал уже не монолит, а новый `hotel-service` (или через API Gateway).

4. **Этап 4 (вынос ReviewService)**
    - Аналогично выделить `ReviewService` в отдельный микросервис, теперь он будет независим (не имеет зависимостей от других сервисов, кроме своей БД).
    - После выноса настроить маршрутизацию на `booking-service`, чтобы он вызывал уже не монолит, а новый `review-service` (или через API Gateway).

4. **Этап 4 (вынос PromoCodeService)**
    - Аналогично выделить `PromoCodeService` в отдельный микросервис, теперь он будет независим (не имеет зависимостей от других сервисов, кроме своей БД).
    - После выноса настроить маршрутизацию на `booking-service`, чтобы он вызывал уже не монолит, а новый `promocode-service` (или через API Gateway).

5. **Этап 5 (вынос AppUserService)**
    - Аналогично выделить `AppUserService` в отдельный микросервис, теперь он будет независим (не имеет зависимостей от других сервисов, кроме своей БД).
    - После выноса настроить маршрутизацию на `booking-service`, чтобы он вызывал уже не монолит, а новый `appuser-service` (или через API Gateway).

5. **Этап 6 (оптимизация и завершение)**
    - Внедрить распределённую трассировку, централизованное логирование.
    - Настроить масштабирование и мониторинг.
    - Провести ретроспективу и оптимизировать взаимодействия.
