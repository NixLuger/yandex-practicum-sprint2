# Стратегия миграции данных при выделении модуля бронирования

## 1. Контекст

В рамках task2 мы выделили модуль бронирования из монолита в отдельный микросервис (`booking-service`) с gRPC-интерфейсом. Монолит продолжает работать, но теперь он может делегировать операции с бронированиями внешнему сервису через прокси-слой (на основе библиотеки `p-o-y-1.0.0.jar`).

В этом документе описывается стратегия миграции данных и конечное состояние (`To Be`) архитектуры.

---

## 2. Текущее состояние (As‑Is)

- Монолит содержит:
    - Таблицу `bookings` в своей БД (PostgreSQL).
    - Логику создания и чтения бронирований в `BookingService`.
    - REST-контроллеры для работы с бронированиями.
- Новый `booking-service` уже развёрнут и принимает gRPC-запросы на порту 9090.
- Монолит может быть сконфигурирован для использования удалённого gRPC-сервиса через переменную окружения `BOOKING_SERVICE_EXTERNAL_HOST`.

---

## 3. Стратегия миграции (How to get there)

### Этап 1. Подготовка нового сервиса

- Развернуть `booking-service` с собственной БД (`booking-service-db`).
- Убедиться, что он работает и готов принимать запросы.
- Создать в новой БД схему, идентичную таблице `bookings` монолита (или расширенную, если требуется).

### Этап 2. Синхронизация данных (миграция исторических данных)

- Выполнить однократный экспорт всех существующих бронирований из таблицы монолита.
- Импортировать их в БД `booking-service` с сохранением идентификаторов (`id`).
- Для этого можно использовать скрипт на Go/Java или утилиту `pg_dump`/`pg_restore` с фильтрацией по таблице.

**Важно:** Идентификаторы должны совпадать, чтобы внешние ссылки (например, на другие сервисы) не нарушились.

### Этап 3. Постепенное переключение трафика (canary + fallback)

В монолите реализован прокси-механизм, который активируется при наличии переменной `BOOKING_SERVICE_EXTERNAL_HOST`. Мы будем использовать его для постепенного переключения:

- **Staging-среда:** включить прокси для небольшой группы пользователей (по заголовку или проценту трафика). Наблюдать за ошибками и задержками.
- **Prod-среда:** начать с 10% трафика через gRPC, остальные 90% — локально. Постепенно увеличивать долю до 100% при отсутствии проблем.

Если возникают ошибки, мы можем мгновенно откатить, убрав переменную окружения (монолит вернётся к локальной реализации).

### Этап 4. Отключение локальной логики

После того как весь трафик переключен на gRPC:

- Удалить (или закомментировать) код локального `BookingService` и его зависимостей.
- Удалить таблицу `bookings` из БД монолита (после периода наблюдения, чтобы убедиться, что она больше не нужна).

---

## 4. Обеспечение согласованности данных (dual-write / eventual consistency)

На время миграции мы можем использовать **dual-write** (запись в обе БД) для новых бронирований:

- Монолит сначала пишет в локальную БД, а затем асинхронно (или синхронно) отправляет запрос на создание в gRPC-сервис.
- Либо наоборот: сначала в gRPC, потом в локальную, с компенсирующими транзакциями при ошибках.

В нашем случае мы выбрали более простой путь: **переключение read/write одновременно через прокси**. Это означает, что в момент переключения мы должны быть уверены, что новые данные пишутся только в одну БД. Для этого мы останавливаем запись в локальную таблицу и используем gRPC как единственный источник истины.

Чтобы избежать потери данных во время переключения, мы можем на короткое время перевести систему в режим «только чтение» (maintenance window) или выполнить миграцию в ночное время с низкой нагрузкой.

---

## 5. Стратегия отката (Rollback)

Если после переключения возникают критические проблемы:

- Вернуть переменную окружения `BOOKING_SERVICE_EXTERNAL_HOST` в монолите (или удалить её) – монолит переключится обратно на локальную реализацию.
- Данные, созданные в gRPC-сервисе за время работы, можно синхронизировать обратно в монолит через обратный скрипт (если это необходимо).
- При отсутствии необходимости возврата данных (если мы можем позволить им остаться в новом сервисе) – просто откатываем прокси и продолжаем использовать локальную логику для новых запросов, а старые данные уже в новом сервисе останутся.

---

## 6. To Be – конечная архитектура

После завершения миграции:

- Монолит **не содержит** кода и таблиц, связанных с бронированиями.
- Все операции с бронированиями выполняются через gRPC-вызовы к `booking-service`.
- В монолите остаётся только прокси-слой (`GrpcBookingService`), который вызывает удалённый сервис.
- `booking-service` полностью отвечает за свои данные, масштабируется независимо.
- В перспективе монолит может быть переписан для прямого вызова gRPC без прокси, но это уже следующая задача.

**Преимущества конечного состояния:**

- Чёткое разделение ответственности.
- Возможность развивать сервис бронирования независимо (например, добавить новые методы или изменить БД).
- Упрощение монолита.

---

## 7. Вывод

Предложенная стратегия миграции минимизирует риски за счёт поэтапного переключения, возможности отката и предварительной синхронизации данных. Она позволяет безопасно выделить модуль бронирования в микросервис без остановки бизнеса.
